## 3. Timezone Fix (2026-07-30)

**Root cause:** `tvDatafeed` returns timestamps in the TradingView session timezone (Europe/Berlin, CEST = UTC+2) as timezone-naive values. `pd.to_datetime(value, utc=True)` treated these as UTC, shifting every intraday bar 2 hours too late in the chart.

**Fix applied in** `tools/market-data/tv_datafeed_collector.py` → `normalize_date()`:
```python
ts = pd.to_datetime(value)
if ts.tzinfo is None:
    ts = ts.tz_localize("Europe/Berlin", ambiguous="NaT", nonexistent="NaT")
ts_utc = ts.tz_convert("UTC")
```

**Verification:** After fix + full re-seed (cleanup + 3rd scrape), FDAX1! 2H last bar = `2026-07-30T10:00:00Z` = 12:00 CEST (correct: current forming 2H bar). 6E1! 30M last bar = `2026-07-30T11:30:00Z` = 13:30 CEST (correct: last completed 30M bar).

## 4. Chart UI

### CrosshairMode fix (2026-07-30, v2)

**Bug (v1):** The data-update `applyOptions` (fires every 5s refresh) was setting `CrosshairMode.Normal`, overriding `CrosshairMode.Magnet` set at `createChart`.

**Bug (v2):** `CrosshairMode.Magnet` (value=1) only snaps the horizontal line to the **close** price. In TradingView the crosshair snaps to any of OPEN/HIGH/LOW/CLOSE on hover.

**Fix applied in** `src/components/monitoring/MonitoringChart.tsx`:
- Changed `CrosshairMode.Magnet` → `CrosshairMode.MagnetOHLC` (LWC v5 value=3) in all three locations:
  1. `createChart` crosshair options (~line 1350)
  2. Hover `applyOptions` (~line 1278)
  3. Data-update `applyOptions` (~line 1765, re-asserted every 5s so refresh cannot revert)
- Crosshair color unified to `rgba(180, 185, 200, 0.6)` (grey) in all three locations

### Scroll / pan (fixed 2026-07-30)

- Mouse wheel: **pan** (TV-style — wheel-down scrolls to older bars, wheel-up to newer bars)
- Drag: **pan** (`handleScroll.pressedMouseMove: true`)
- `handleScale.mouseWheel: false` in both `createChart` and data-update `applyOptions` (prevents 5s refresh re-enabling zoom-on-wheel)
- Custom `onWheel` handler: horizontal δX pans time axis; vertical δY pans time axis (VERTICAL_WHEEL_BAR_SHIFT = 3 bars per tick)
- Touch: pinch zooms, drag pans (`horzTouchDrag: true, vertTouchDrag: true`)

## 5. OHLC Quality Controls

### validateAndRepairOhlc (`src/lib/market-data/ohlc-quality.ts`)

| Check | Condition | Action |
|-------|-----------|--------|
| `non_finite` | NaN/Infinity in any OHLC field | quarantine |
| `non_positive` | any field ≤ 0 | quarantine |
| `future_timestamp` | `time > now + 60s` | quarantine |
| `close_outlier` | `close < max(p90*0.1, maxClose*0.02)` | quarantine |
| `wick_outlier` | `low < close*0.2` or `high > close*5` | quarantine |

### pruneStaleTickBars
If any non-tick bars exist (`hasHistory=true`), ALL tick-built rows are removed. This is why the old YM1! corrupt tick bar (which showed ~515) is no longer present after the Yahoo Finance seed.

### filterPriceOutliers (route.ts line ~131)
**Dead code** — defined but never called. The equivalent logic runs inside `validateAndRepairOhlc`. Should be removed in a future cleanup.

## 6. YM1! Corrupt Bar — Root Cause

The screenshot (14:24 CEST, 2026-07-30) showed a bar dropping from ~52,000 to ~515. Investigation:

- **Supabase data (full scan, 6211 rows):** 0 corrupt rows, all close values 10,000–60,000 range.
- **Public cache (`CBOT_MINI_YM1_D.json`):** 0 corrupt rows.
- **API route:** passes through `validateAndRepairOhlc` which quarantines `close < max(p90*0.1, maxClose*0.02)`.

**Most likely cause:** An old tick-built row with `date` ending in `Z` survived in `monitoring_ohlc` before the Yahoo Finance seed. After seeding, `pruneStaleTickBars(isDaily=true)` removed it because `hasHistory=true` (>0 non-tick rows exist). The screenshot was captured before the next Vercel deployment propagated.

**Current status:** ✅ Resolved. Hard refresh (Ctrl+F5) should show clean data.
